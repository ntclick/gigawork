# ERC-8004: Identity, Reputation & Validation

> **Manus note:** File này mô tả 3 module của ERC-8004. Cần 4 diagram:
> 1. Quan hệ giữa IdentityRegistry, ReputationRegistry, ValidationRegistry
> 2. Flow mint identity NFT (user-initiated)
> 3. Flow giveFeedback (reputation increment sau workflow)
> 4. Flow validationRequest + validationResponse (agent proof)

## Tổng quan

ERC-8004 là chuẩn "Agent Proofs" của Arc — cung cấp hạ tầng on-chain để:
1. **Identity:** Đăng ký agent với NFT định danh (ERC-721)
2. **Reputation:** Ghi nhận điểm uy tín sau mỗi công việc hoàn thành
3. **Validation:** Xác thực và lưu bằng chứng công việc on-chain

## 1. Identity Registry

**Contract:** `$IDENTITY_REGISTRY_ADDRESS` (set trong env)

### Mint NFT Identity

Người dùng và skill agent đều cần có Identity NFT để tham gia hệ thống.

**User flow:**

> **Manus note:** Vẽ sequence diagram mint identity. Actors: User, Browser, IdentityGate component, /api/identity/prepare, /api/identity/confirm, Arc Chain.

```
/api/identity/prepare
  → prepareMintCalldata(userWallet)
  → trả về: { calldata: encode register(agentURI), contract, agentURI }
  agentURI = "${APP_URL}/agent/${wallet.toLowerCase()}"

User ký tx: IdentityRegistry.register(agentURI)
  → emit Registered(tokenId, owner, agentURI)
  → emit Transfer(0x0, owner, tokenId)

/api/identity/confirm
  → verifyMintTx(txHash, expectedOwner)
      1. Chờ receipt (1 confirmation, 60s timeout)
      2. Parse Registered + Transfer events → lấy tokenId
      3. Verify ownerOf(tokenId) == expectedOwner
  → UPDATE users SET identity_token_id=tokenId, identity_tx_hash=txHash
  → Gọi grantSignupBonus(userId) → +300 credits lần đầu
```

**Skill agent flow (admin mint):**

```
scripts/mint-agents.ts
  Với mỗi skill chưa có agent_token_id:
  1. Upload metadata JSON lên IPFS (name, description, endpoint, category)
  2. Admin ký: IdentityRegistry.register(ipfsURI)
  3. Lưu tokenId + txHash vào skills.agent_token_id
```

### Auto-sync Identity (checkOnChainIdentity)

Hàm `checkOnChainIdentity(wallet)` được gọi tại:
- `/api/workflow` khi tạo workflow mới
- `/api/me` khi user load trang

```
1. Kiểm tra in-memory cache (TTL=30s)
2. Nếu cache miss: balanceOf(wallet) → enumerate tokens via tokenOfOwnerByIndex
3. Trả về tokenId thấp nhất (oldest/canonical)
4. Cache 30s
```

### ABI Functions

```solidity
function register(string agentURI) external returns (uint256 agentId)
function ownerOf(uint256 tokenId) external view returns (address)
function balanceOf(address owner) external view returns (uint256)
function tokenOfOwnerByIndex(address owner, uint256 index) external view returns (uint256)
```

## 2. Reputation Registry

**Contract:** `0x8004B663056A597Dffe9eCcC1965A193B7388713`

### Cơ chế hoạt động

Sau mỗi workflow hoàn thành, admin gọi `giveFeedback` cho:
- Mỗi skill agent token được sử dụng (`skills.agent_token_id`)
- Identity token của user (`users.identity_token_id`)

> **Manus note:** Vẽ diagram luồng reputation sau workflow complete. Bao gồm cả DB update (SQL `+1`) và on-chain `giveFeedback`. Chú ý luồng kép: cacheReputation() trong finalizeWorkflow + reconcile endpoint nếu cần retry.

### Score values

| Trường hợp | Score | feedbackType | tag |
|-----------|-------|-------------|-----|
| Workflow hoàn thành | `+95` | `0` (task_completed) | `workflow_settled` |
| Workflow thất bại | `-50` | `1` (task_failed) | `workflow_failed` |

### Luồng chính

```
publishFinalReport()
  → cacheReputation(workflowId, userId)
      1. Query tất cả completed nodes + skill agentTokenId
      2. SQL UPDATE: skills.reputation_score += 1 (DB cache)
      3. SQL UPDATE: users.reputation_score += 1 (DB cache)
      4. incrementReputationBatch([tokenId1, tokenId2, ...], "completed")
          Với mỗi tokenId:
            giveFeedback(agentId=tokenId, score=95, feedbackType=0,
                         tag="workflow_settled", metadataURI="", evidenceURI="",
                         comment="", feedbackHash=keccak256("workflow_settled"))
            Chờ receipt (1 confirmation, 90s timeout)
            Nếu revert: log + skip (ERC-8004 self-dealing rule)
          Trả về hash của tx đầu tiên thành công
      5. INSERT messages (toolName=reputationUpdate, toolPayload={tx, status})
```

### Self-Dealing Rule

ERC-8004 **ngăn** owner của agentId gọi `giveFeedback` cho chính agent đó.

Trong triển khai hiện tại:
- Nếu admin owns skill tokens → `giveFeedback` sẽ revert on-chain
- Code catch revert per-token và `continue` (không block toàn bộ batch)
- DB score vẫn được tăng (SQL UPDATE chạy trước on-chain call)
- UI hiển thị "done (DB only)" thay vì "pending"

> **Manus note — TODO:** Cần quyết định chiến lược lâu dài:
> - Option A: Transfer skill tokens sang non-admin wallet (owner ≠ signer → `giveFeedback` thành công)
> - Option B: Dùng một "reviewer key" riêng biệt không own token nào
> - Hiện tại DB score vẫn hoạt động đúng, chỉ on-chain tx bị skip

### Reconciliation (Safety Net)

Nếu `cacheReputation` không chạy (brain crash, network lỗi), page load sẽ retry:

```
page.tsx useEffect (khi workflow completed/failed):
  POST /api/workflow/[id]/reputation/reconcile
  → Kiểm tra: có reputationUpdate message chưa?
  → Nếu chưa: chạy lại toàn bộ cacheReputation logic
  → Nếu rồi: trả về { already: true }
  → Sau khi xong: gọi setMessages() để Canvas/DocPanel cập nhật UI
```

### ABI Function

```solidity
function giveFeedback(
  uint256 agentId,
  int128 score,
  uint8 feedbackType,
  string tag,
  string metadataURI,
  string evidenceURI,
  string comment,
  bytes32 feedbackHash
) external

  uint256 indexed agentId,
  address indexed reviewer,

  uint8 feedbackType,
  string tag,
  bytes32 feedbackHash
```

## 3. Validation Registry (Agent Proofs)

**Contract:** `0x8004Cb1BF31DAf7788923b405b754f57acEB4272`
**Gated by:** `VALIDATION_REGISTRY_ADDRESS` env (nếu không set → bỏ qua)

### Mục đích

Ghi bằng chứng công việc on-chain: agent X đã hoàn thành công việc Y. Cặp `validationRequest + validationResponse` tạo thành một "proof" không thể sửa đổi.

> **Manus note:** Vẽ diagram luồng validation. Actors: finalizeWorkflow.ts, ValidationRegistry contract. Chú ý: chỉ chạy sau reputation, và chỉ cho token admin own.

### Luồng

```
cacheReputation() → attestWorkflowCompletion(workflowId, agentIds)
  Với mỗi agentId:
    1. ownerOf(agentId) == adminAccount? 
       Nếu không: skip với reason="owner_mismatch"
    2. requestHash = keccak256(workflowId + agentId + "workflow_completed")
    3. validationRequest(validator=admin, agentId=agentId,
                         requestURI="", requestHash=requestHash)
       → emit ValidationRequested(requestHash, validator, agentId)
    4. validationResponse(requestHash=requestHash, response=100,
                          responseURI="", responseHash=requestHash,
                          tag="workflow_completed")
       → emit ValidationResponded(requestHash, response=100)
  INSERT messages (toolName=validationAttest, toolPayload=[results])
```

### Response Code

| Code | Ý nghĩa |
|------|---------|
| `100` | PASSED (theo ERC-8004 spec) |
| `0` | Chưa có response |
| Khác | Custom application semantics |

### Lưu ý

- **Best-effort:** Failure không block workflow completion
- **Chỉ admin-owned tokens:** Khác với reputation (skip tất cả), validation CHỈ chạy cho tokens admin own (ownership check ngược chiều)
- **Runs AFTER reputation:** Nếu reputation fails → validation không chạy

### ABI Functions

```solidity
function validationRequest(
  address validator,
  uint256 agentId,
  string requestURI,
  bytes32 requestHash
) external

function validationResponse(
  bytes32 requestHash,
  uint8 response,
  string responseURI,
  bytes32 responseHash,
  string tag
) external

function getValidationStatus(bytes32 requestHash)
  external view returns (address validator, uint256 agentId, uint8 response, string tag)
```

## Quan hệ giữa 3 module

> **Manus note:** Vẽ sơ đồ quan hệ (entity relationship hoặc component diagram):
>
> - `IdentityRegistry` cấp `tokenId` cho cả User và Skill
> - `ReputationRegistry` nhận `agentId` (= tokenId từ IdentityRegistry) để ghi điểm
> - `ValidationRegistry` nhận `agentId` + `requestHash` để tạo proof
> - `agenticCommerce` (ERC-8183) hoạt động song song, không phụ thuộc vào ERC-8004

```
IdentityRegistry
    ├── issues tokenId to USER → users.identity_token_id
    └── issues tokenId to SKILL → skills.agent_token_id
                │
                ├──→ ReputationRegistry.giveFeedback(agentId=tokenId)
                │      Cả user + skill đều nhận feedback
                │
                └──→ ValidationRegistry.validationRequest/Response(agentId=tokenId)
                       Chỉ admin-owned tokens (skill agents)
```
